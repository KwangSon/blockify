# Blender Add-on Design

## Product Model

Blockify is a native Blender add-on.

The primary UX is interactive and should feel similar in philosophy to Blender generation add-ons such as Rigify:

```text
Source Object
     +
Generation Settings
     ↓
Generate / Regenerate
     ↓
Generated Result
```

Do not design the project around a command-line interface.

## Blender Version

Target Blender 4.x extension/add-on conventions.

Use `blender_manifest.toml` for modern extension packaging where appropriate.

The exact minimum supported Blender version must be declared before the first release and tested explicitly.

## Registration

Keep registration organized.

`__init__.py` should primarily:

- load internal modules
- register classes
- register properties
- unregister in reverse order

Do not place generation algorithms in `__init__.py`.

## Operators

Initial operators:

```text
blockify.generate
blockify.regenerate
```

Possible later operators:

```text
blockify.delete_generated
blockify.select_source
blockify.select_generated
```

Operators are controllers.

A Blender operator should:

1. validate Blender context
2. collect source/settings
3. invoke generation code
4. report success/failure

It should not contain voxel algorithms, clustering implementations, or mesh decomposition logic.

## Poll / Validation

`Generate` should only be available when the context is valid.

At minimum:

- active object exists
- active object type is `MESH`
- source is not itself an incompatible generated result
- block size is valid

Give useful error messages.

Bad:

```text
Generation failed.
```

Better:

```text
Blockify: estimated voxel grid is 124 million cells.
Increase Block Size and try again.
```

## UI Location

Initial UI:

```text
3D Viewport
→ Sidebar (N)
→ Blockify tab
```

Suggested structure:

```text
BLOCKIFY

Source
  Active: Chair

Geometry
  Block Size      [0.10]
  Fill Interior   [✓]
  Merge Cuboids   [✓]

Color
  Preserve Color  [✓]
  Palette Size    [8]

Generate
  [ BLOCKIFY ]

Generated Result
  Cuboids          124
  Palette Colors     8
  Faces            612

  [ REGENERATE ]
```

Avoid exposing algorithmic/debug options by default.

Advanced/debug settings may live in a collapsed section.

## Settings Ownership

Prefer settings associated with the source/generation relationship rather than only global scene state.

A user should be able to have:

```text
Chair
  block_size = 0.20

Sushi
  block_size = 0.05
```

in the same `.blend`.

Implementation may use object properties and/or a dedicated `PropertyGroup`.

The UX requirement is that changing between source objects restores their relevant Blockify settings.

## Source Integrity

Generation must not:

- apply modifiers to source destructively
- rewrite source materials
- alter source mesh vertices
- change source UVs
- rename source object without explicit reason

The source is input data.

If temporary evaluated meshes are created, they must be cleaned up correctly.

## Generated Result Naming

Suggested:

```text
Source:    Tamago
Generated: Tamago_BLOCKIFIED
```

If a collision occurs, Blender-safe naming may be used, but internal linkage must not rely only on the visible name.

## Generated Result Metadata

Mark generated output clearly.

The implementation should be able to answer:

- Is this object generated by Blockify?
- Which source created it?
- Which settings created it?
- Which Blockify schema/version created it?

This is required for safe regeneration.

## Regenerate Semantics

`Regenerate` should behave as a transaction.

Preferred sequence:

1. locate source and old generated result
2. validate source/settings
3. generate a new result
4. if successful, replace/remove old result
5. if failed, keep old valid result

Do not delete the user's last valid output before the new generation has succeeded if avoidable.

## Undo

Generation should integrate sensibly with Blender Undo.

A single user-facing Generate action should not require dozens of undo presses.

Avoid leaking temporary objects/datablocks that survive undo unexpectedly.

## Progress and Responsiveness

Large grids can take noticeable time.

The implementation should:

- estimate unsafe workloads before generation
- update progress if practical
- avoid freezing Blender due to obviously unreasonable settings
- allow future optimization without changing the public generation contract

## Blender Data Management

Be disciplined about datablocks.

When regeneration removes generated data:

- unlink objects correctly
- remove orphaned temporary meshes/materials when owned by Blockify and safe to remove
- never remove source-owned materials/data
- avoid accumulating `Mesh.001`, `Mesh.002`, etc. after repeated generation

Repeated Generate/Regenerate should not cause unbounded data leakage.

## Rigify-inspired Principle

The most important idea borrowed from Rigify is not its rig-specific code.

It is the **generated-system model**:

> The user edits the source and parameters. The add-on owns the generated result.

Blockify should preserve that mental model throughout the implementation.
